# 部署手册：杭州外企设计岗日报

> 目标：每天早上 8:30 自动把「杭州外企 UX/交互/产品设计」岗位推到微信 / 飞书。
> 全流程跑在 GitHub Actions 上，**零服务器、零费用、零运维**。

---

## 一、你需要准备的账号（都在免费额度内）

| 用途 | 平台 | 费用 | 说明 |
|---|---|---|---|
| 定时运行 | GitHub 账号 | 免费 | 公开仓库 Actions 不限时长 |
| 微信推送 | [PushPlus](https://www.pushplus.plus/) | 免费 200 条/天 | 扫码登录即得 token |
| 飞书推送 | 飞书群机器人 | 免费不限量 | 5 分钟配好 |

**建议两个都配**：微信每天能收到（手机上有推送），飞书作为备份（消息更长、链接可点）。任一成功就算发送成功。

## 二、第一步：PushPlus 拿 token（推微信）

1. 打开 https://www.pushplus.plus/
2. 点「登录」，用**微信扫码**
3. 登录后点顶部「一对一推送」，页面上会显示一串 **token**（32 位字符）
4. 复制下来，形如 `a1b2c3d4e5f6...`

> 免费版每天 200 条，我们每天只发 1 条，完全够用。

## 三、第二步：飞书群机器人拿 webhook

1. 打开飞书，进入你想接收日报的**群**（可以自己建一个只有自己的群，比如"招聘日报"）
2. 群设置 → 群机器人 → 添加机器人 → 选「**自定义机器人**」
3. 名字填「招聘日报」，点添加
4. 复制弹出的 **Webhook 地址**，形如：
   ```
   https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
   ```
5. （可选）如果勾选了「**签名校验**」，把下面那个 **密钥** 也复制下来

## 四、第三步：把项目传到你的 GitHub

### 方式 A：网页上传（最简单，不需要装任何软件）

1. 登录 GitHub，右上角 `+` → **New repository**
2. 仓库名填 `job-radar`，选 **Public**（私有仓库 Actions 有免费额度限制，公开最省心）
3. 创建后点「**uploading an existing file**」
4. 把 `job-radar` 文件夹里的**所有内容**拖进去（注意：要拖文件夹里面的东西，不要拖整个文件夹）
5. 点 **Commit changes**

> ⚠ `.github` 文件夹是隐藏的，网页上传时如果拖不进去，用方式 B。
>
> **实测结论：方式 A 基本走不通。** 网页拖拽会把文件路径压平（`job_radar/adapters/workday.py`
> 变成根目录的 `workday.py`），而且 `.github` 无法选中 —— 没有它就没有定时任务，
> 也永远看不到「Run workflow」按钮。**请直接用方式 B**（或双击项目里的 `push.bat`）。

### 方式 B：命令行（推荐，不会漏文件）

```bash
cd job-radar
git init
git add -A
git commit -m "init: 杭州外企设计岗日报"
git branch -M main
git remote add origin https://github.com/<你的用户名>/job-radar.git
git push -u origin main
```

## 五、第四步：配置 Secrets（关键）

进入你的仓库 → **Settings** → 左侧 **Secrets and variables** → **Actions**

### 5.1 添加 Secrets（点「New repository secret」）

逐条添加：每条 = 一次「New repository secret」→ Name 填左列、Secret 填中列 → Add secret。

| Name | Value | 必填 |
|---|---|---|
| `PUSHPLUS_TOKEN` | 第二步复制的 token | 想收微信就填 |
| `FEISHU_WEBHOOK_URL` | 第三步复制的 webhook | 想收飞书就填 |
| `FEISHU_SECRET` | 飞书签名密钥（没开签名校验就不填） | 可选 |
| `LLM_API_KEY` | 智谱 API Key（5.3 有注册步骤） | 可选，不填也能跑 |

> `LLM_BASE_URL` 和 `LLM_MODEL` **不用填了**——代码默认就是智谱
> GLM-4-Flash（永久免费），只填 Key 即可。想换别家才需要另填这两个。

### 5.2 添加 Variables（切到 **Variables** 标签页，点「New repository variable」）

| Name | Value |
|---|---|
| `WORKBENCH_URL` | `https://<你的用户名>.github.io/job-radar/` |

> 这个变量会让日报末尾附上信息台链接，点开能看到全部岗位的网页版。

### 5.3 要不要配大模型 Key？（可选，推荐配免费的）

**不配**：跑规则版。中文 JD 能出中文要点；英文 JD 只出结构化事实
（`5 年以上 · 本科 · Figma`）+ 一行「英文原文要点，未翻译」。零成本、零延迟、
100% 不编造，但英文岗位读起来要靠点链接。

**配**：英文 JD 也能压成通顺的中文两三句，播报短一半、可读性高一档。

**推荐：智谱 GLM-4-Flash，永久免费、不限量、OpenAI 兼容、国内直连**。
本系统每天只调几次、约 2 万 token，免费额度绰绰有余：

1. 打开 https://open.bigmodel.cn/ → 手机号注册
2. 右上角头像 → 「API Keys」→ 新建 → 复制（形如 `xxxxxxxx.xxxxxxxx`）
3. 仓库 Secrets 里加一条：Name 填 `LLM_API_KEY`，Value 粘贴刚复制的 Key
4. 完事。`LLM_BASE_URL` / `LLM_MODEL` 代码里已默认指向智谱，不用填

备选（万一哪天智谱不好使，改两个 Secrets 即可切换）：

| 平台 | LLM_BASE_URL | LLM_MODEL | 免费额度 |
|---|---|---|---|
| 硅基流动 | `https://api.siliconflow.cn/v1` | `Qwen/Qwen2.5-7B-Instruct` | 9B 以下模型永久免费 |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` | 送 500 万 token（约够半年） |

**安全边界（代码里写死的，不靠模型自觉）**：

- Prompt 只允许「压缩 + 翻译」，禁止推测薪资、公司规模、团队情况
- 输出里出现的每个数字，都会和原文数字集合比对，对不上就**整条丢弃**，退回规则版
- 「有竞争力的薪资」「广阔发展空间」这类套话命中黑名单直接判废
- 无 key / 超时 / 校验失败 → 静默降级到规则版，**永不阻塞播报**

所以配了 Key 也不会出现编造的岗位信息；最坏情况就是回到不配 Key 的效果。

## 八、验证定时是否生效

`Actions` → `job-radar-sync` → 左侧列表里能看到 `schedule` 触发的运行记录。

每天北京时间 **08:30** 自动跑，配置在 `.github/workflows/sync.yml`：

```yaml
on:
  schedule:
    - cron: "30 8 * * *"
      timezone: "Asia/Shanghai"
```

> ⚠ 注意：GitHub 从 2026-03 起支持 `timezone` 字段。**一旦写了 timezone，cron 就按北京
> 时间解释**，所以是 `30 8`（8:30）而不是 `30 0`（那是旧写法，靠 UTC 换算）。
> 如果你把 timezone 删掉，cron 就回到 UTC，必须改回 `30 0`。

## 九、日常怎么用

### 看当天推送内容

- 微信 / 飞书收到的消息
- 或打开 `https://<你的用户名>.github.io/job-radar/`

### 加一家新公司

1. 打开这家公司的招聘官网（careers 页面），复制网址
2. 本地跑探测：
   ```bash
   python3 scripts/probe.py "https://xxx.com/careers"
   ```
3. 如果输出里「命中」> 0，它会打印一行 CSV，粘到 `config/sources.csv` 里，提交即可

### 调整筛选口味

编辑 `config/profiles.json`：

| 字段 | 作用 |
|---|---|
| `cities` | 城市范围，想加苏州/南京就往里加 |
| `min_score_to_push` | 推送门槛，默认 55，调低=更多（也更杂） |
| `target_roles` | 目标岗位名 |
| `exclude_roles` | 排除的岗位（平面/室内/工业设计等） |
| `must_keywords` / `nice_keywords` | 命中就加分的关键词 |
| `attr_bonus` | **岗位属性权重**（见下表） |

改完提交，下次运行即生效。

### 岗位属性怎么筛（attr_bonus）

岗位的常见属性（职级、雇佣形式、办公方式、设计方向、语言要求）由
`job_radar/job_attrs.py` 从**标题和地点**里识别，识别结果不影响真假，
只影响排序和分数。权重在 `config/profiles.json` 的 `attr_bonus` 里配：

| 属性 key | 含义 | 默认分 |
|---|---|---|
| `level:intern` | 实习 | −60 |
| `level:junior` | 初级 / 应届 | −8 |
| `level:senior` | 资深 / 高级 | +8 |
| `level:lead` | Lead / 负责人 | +12 |
| `level:manager` | 经理 / 主管 | +12 |
| `level:staff` / `level:principal` | Staff / 首席 | +12 / +14 |
| `level:director` | 总监 / Head of | +14 |
| `employment:internship` | 实习（雇佣形式） | −40 |
| `employment:part_time` | 兼职 | −20 |
| `employment:contract` | 外包 / 合同制 | −12 |
| `employment:full_time` | 全职 | +2 |
| `mode:remote` | 远程 | +8 |
| `mode:hybrid` | 混合办公 | +3 |
| `lang:english` | 要求英语 | +8 |
| `lang:bilingual` | 中英双语 | +10 |
| `func:ux_research` | 用户研究 | +6 |
| `func:design_system` | 设计系统 | +4 |
| `func:content_design` | 内容设计 / UX Writer | +4 |
| `func:service_design` | 服务设计 | +4 |
| `func:design_ops` / `func:accessibility` / `func:motion` | 设计运营 / 无障碍 / 动效 | +2 |

规则说明：

- **属性总分封顶 ±24**（负向最低 −60），避免「资深+远程+英语+设计系统」叠出几十分，
  把公司层级和方向匹配的差异抹平
- 属性**只能加分或减分，不能突破门槛**：非设计岗依然是 0 分，实习岗也压不到负数后自动复活
- 现在的画像（英语无障碍、加拿大 8 年、硕士）已经把 `lang:english` / `lang:bilingual`
  设成**加分项而不是门槛**——需要英语的岗位对她是优势，不是障碍
- 想让某类彻底别出现，别改 `attr_bonus`，去 `negative_keywords` 或 `exclude_roles`

---

### 播报里那行属性标签是哪来的

卡片第二行的 `全职 · 资深 · 职位号 R075434`：

- `全职` 来自 Workday 的 `timeType` 字段（真实数据）
- `资深` 来自标题里的 "Senior"，识别口径在 `job_radar/job_attrs.py`
- `职位号` 来自 `jobReqId`，可以拿它去官网反查这条岗位

没有识别出来的属性**不会硬凑**（比如标题没写职级就不显示职级）。

## 十、故障排查

| 现象 | 原因 | 解决 |
|---|---|---|
| Actions 跑完但没收到消息 | Secrets 没配对，或名字拼错 | 检查 Settings → Secrets，名字必须完全一致 |
| 微信收到但内容是空的 | `PUSHPLUS_TOKEN` 失效 | 重新扫码拿 token |
| 飞书报 `sign match fail` | 开了签名校验但没填 `FEISHU_SECRET` | 补上密钥，或关掉机器人签名校验 |
| 飞书报 `19021` | webhook 地址复制少了字符 | 重新复制完整地址 |
| 每天收到但都是「今日无新增」 | 正常现象，见下方说明 | —— |
| Actions 显示 `schedule` 但时间不对 | 时区配置 | 见第八节 |
| 同步步骤报 `探针失败` | 某家外企改了 ATS 地址 | 把该行 `status` 改 `blocked` 先停掉 |
| 播报里写「官网未提供职位描述」 | 这家 Workday 的详情接口不返回正文 | 正常，点链接去官网看 |
| 播报末尾出现「已排除」 | 标题与正文不符 / 链接连续 3 次打不开 | 正常，是自动校验在挡假岗位 |
| 想确认某条岗位真假 | —— | 卡片里有「职位号」，去官网搜这个号最准 |
| Actions 页看不到「Run workflow」按钮 | 仓库里没有 `.github/workflows/sync.yml`（网页上传时隐藏文件夹拖不进去） | 用命令行推送完整结构，见下方「结构被打平了怎么办」 |
| 仓库根目录散着一堆 `.py`，没有 `job_radar/` 文件夹 | 网页上传时拖的是文件夹**里面的文件** | 同上，用 `push.bat` 重新推一遍，会整体覆盖 |

### 结构被打平了怎么办（网页上传的通病）

网页上传有两个限制：拖文件夹时只上传里面的文件（路径丢失）；隐藏目录 `.github` 根本选不中。
所以**网页上传这套项目一定会失败**，必须用命令行。本机已经替你初始化好 git 仓库，
只需要在项目目录里双击 `push.bat`（或手动执行 `git push -f -u origin main`）：

- 第一次会弹出 GitHub 登录窗口 → 点 **Sign in with browser** → 浏览器里授权即可
- 如果弹窗里让你填密码，密码位置要填 **Personal Access Token**（不是账号密码）：
  GitHub 右上头像 → Settings → 最底 **Developer settings** → **Personal access tokens** →
  **Tokens (classic)** → **Generate new token (classic)** → 勾 `repo` → 生成后复制 `ghp_...`
- 用 `-f` 强制推送是有意的：仓库里现在那批打平的文件会被**整体替换**成正确结构

推成功后，仓库根目录应该是 `job_radar/`、`scripts/`、`config/`、`.github/`、`docs/`、`data/`
这几个文件夹，而不是一堆散落的 `.py`。

## 十一、重要：为什么很多时候是「今日无新增」

这是**真实情况，不是 bug**。

实测（2026-10-22）：扫描 15 家外企官网（辉瑞、道富、RingCentral、Zoom、应用材料、
英特尔、恩智浦、雅培、3M、科磊、阿斯利康、英伟达、丹纳赫、美敦力等）全量岗位，
杭州 + 设计岗**只有 3-5 条**。

所以播报设计成**两层**：

1. **新增**：今天新出现的岗位（多数天为 0）
2. **近14天热招（存量兜底）**：只要还在架、近 14 天更新过、达标，就固定带几条

这样即使某天没有新增，你也能收到一份「当前在招清单」，不会空手。

如果你觉得存量重复太多，可以关掉：

```yaml
# .github/workflows/sync.yml 里
run: python3 scripts/send_notify.py --no-standby
```

## 十二、这份播报是怎么「可信」的

内容不是模型编的，全部能回查官网。整条链路分四步，每步都能单独跑：

```bash
python3 scripts/sync_plan.py fast     # 1) 抓列表 → data/jobs.json（打分、去重、判在架）
python3 scripts/enrich_jd.py          # 2) 回查详情接口 → data/jd_cache.json（JD 正文/发布日期/职位号）
python3 scripts/verify_links.py       # 3) 判链接生死 → data/link_health.json
python3 scripts/notify_preview.py     # 4) 出播报 → data/notify_preview.md
python3 scripts/send_notify.py        # 5) 推送三通道
```

几个刻意的设计：

| 现象 | 为什么这么做 |
|---|---|
| 播报里没有「匹配 181」这种分 | 分数是内部相对指标，露出来只会让人怀疑「这数怎么算的」 |
| 发布日期写 `2026-08-14 发布（70 天前）` | 来自 Workday 的 `startDate` 真实字段，不是我们猜的 |
| 没发布日期就**不写**这一行 | 绝不用「首次抓到的时间」冒充发布时间 |
| 老岗位加 `⚠ 已挂 105 天` | 提示而不是隐藏，投不投由人决定 |
| 英文 JD 标「英文原文要点，未翻译」 | 没配大模型时如实说明，不假装翻译过 |
| 抓不到 JD 就写「官网未提供职位描述」 | 不猜、不编 |
| 文末有「已排除」小节 | 被剔除的岗位和原因都写出来，不静默消失 |
| 链接连续 3 天才剔除 | 偶发 503 不算数，且 403 只标「无法判定」，不冤枉好岗位 |

想本地看效果（不推送、不写推送状态）：

```bash
python3 scripts/notify_preview.py --ignore-state
cat data/notify_preview.md
```

## 十三、成本与稳定性

| 项目 | 用量 |
|---|---|
| GitHub Actions | 每次约 5-8 分钟，每天 1 次 → 月均 200 分钟（公开仓库免费无限） |
| PushPlus | 每天 1 条 → 月均 30 条（免费额度 200 条/天） |
| 飞书机器人 | 免费不限量 |
| 大模型（可选） | 约 ¥0.003/天；不配 Key 为 0 |
| 服务器 | 无 |

> GitHub 的定时任务在高峰期可能延迟几分钟到半小时，属正常现象。
> 长期无提交的仓库，Actions 定时任务可能在 60 天后被自动停用——届时手动点一次
> `Run workflow` 即可恢复，或随便提交一次改动。
